A provider call fails. Maybe the model is rate limited, or the service returned a 503. Your application still needs an invoice.

You could wrap every call site in retry code. Instead, declare the policy once on the **profile**. A profile can retry its own model, then **fall back** to a second profile that uses a different model or provider. The command call site does not change.

## What happens on a failure?

The router classifies each failure, then decides what to do.

| Failure | Examples | Retries? | Falls back? |
| --- | --- | --- | --- |
| **Transient** | HTTP 5xx, 408, a network error | Yes | After retries |
| **RateLimited** | HTTP 429 | Yes | After retries |
| **Timeout** | An attempt deadline, a provider-side cancellation you did not request | Yes | After retries |
| **Permanent** | Any other error, such as a bad request | No | No |
| **Cancelled** | Your cancellation token | No | No |

A permanent failure does not fall back. A different model cannot fix a request the provider rejected. Cancellation stops routing at once.

## Declare the policy

Register two clients, then give the primary profile a retry policy and a fallback:

```csharp [Program.cs]
services.AddKeyedChatClient("openai", _ => primaryClient);
services.AddKeyedChatClient("claude", _ => backupClient);

services
    .AddAgentCmd(options =>
        options
            .AddChatClient("openai")
            .AddChatClient("claude")
            // The backup route. It can have its own retry policy.
            .AddProfile("review", "claude", "synthetic-claude")
            .AddProfile(
                "extraction",
                "openai",
                "synthetic-model",
                retry: new RetryPolicy(MaxRetries: 2, TimeSpan.FromMilliseconds(200)),
                // Used after the retries are exhausted.
                fallback: ProfileKey.Declare("review"),
                attemptTimeout: TimeSpan.FromSeconds(30)
            )
            // Total attempts across retries and fallback.
            .UseBudget(new ExecutionBudget(MaxAttempts: 4))
            .UseDefaultProfile("extraction")
            .UseActor(_ => actor)
    )
    .AddGeneratedCommands();
```

In this setup:

- The first attempt goes to `extraction`.
- A transient failure retries that profile up to two times, with exponential backoff that starts at 200 ms.
- If the third attempt also fails, the router calls `review` on the other client.
- The budget caps the whole route at four attempts. The budget does **not** restart on fallback.

The fallback profile uses its **own** defaults, such as temperature. Explicit settings from the caller, such as `WithTemperature`, still apply to every attempt. A fallback is never chosen by guessing a model name. You name it.

::note
Put the fallback on a different client or provider. A fallback on the same failing service shares its outage.
::

## Call it

The call site is the same as without a policy:

```csharp [Call site]
var outcome = await extract
    .WithParameters(new InvoiceInput(document))
    .ExecuteAsync(ct); // Retries and fallback happen inside.
```

## See what happened

A successful outcome records the route. Use it to find out whether the primary profile served the call:

```csharp [Inspect the route]
if (outcome is Outcome<Invoice>.Success { Snapshot.Routing: { } route })
{
    // ServedProfile is "review" when the fallback answered.
    Console.WriteLine($"{route.RequestedProfile} -> {route.ServedProfile}");

    foreach (var attempt in route.Attempts)
    {
        // Kind is initial, retry or fallback. Outcome says how that attempt ended.
        Console.WriteLine($"{attempt.Number} {attempt.Kind} {attempt.Profile} {attempt.Outcome}");
    }
}
```

With `MaxRetries: 2`, a call where the primary keeps failing makes three primary attempts. The fallback is the fourth, so the kinds read `initial`, `retry`, `retry`, `fallback`.

The same evidence reaches your telemetry:

- Each provider call has its own `agentcmd.provider.attempt` span under the command's `agentcmd.execute` span.
- The command span gets one `agentcmd.profile.fallback` event when the route changes profiles.
- The `agentcmd.profile.fallbacks` counter increments, tagged with the reason, such as `Transient`.

See [Telemetry and evaluation capture](/guides/accounting-and-observability) for how to export these. Place attempt capture inside retry and fallback, so it sees each real provider call.

## What does setup reject?

The router validates profiles when it is built, before any paid call:

- A fallback to a profile that is not configured.
- A fallback cycle, such as `a` falling back to `b` and `b` back to `a`.
- A profile that names a client that is not registered. The [analyzer](/guides/profiles-and-clients) reports straightforward cases at build time.

If every route fails, `ExecuteAsync` returns `Outcome<T>.Failed` with a `ProviderFailure`. Its snapshot keeps the same route evidence, so you can see every attempt. See [Outcomes and context](/guides/outcomes-and-context).

The [profile tests](https://github.com/zeeq-ai/zeeq-agentcmd/blob/main/tests/AgentCmd.CommandRoot.Tests/ProfileTests.cs) exercise retry, fallback, budget and cancellation with fake clients.
