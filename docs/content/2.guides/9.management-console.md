A model returns a suspicious result. Start in **Traces** to inspect the retained execution. When a reviewer returns later, use **Datasets** and **Review** to curate a regression case. Use **Experiments** when you are ready to evaluate a frozen dataset.

These are separate actions. The application executes the command and reports evidence. A reviewer selects cases and supplies expected answers. An evaluation worker claims work only after an operator launches a job.

## Open a local workspace

Run from the repository root. Start the API and console in separate terminals.

```sh
mise run console:install
mise run console:api:local
```

```sh
AGENTCMD_API_PROXY=http://127.0.0.1:5180 mise run console:dev
```

Open the URL printed by Vite, usually `http://127.0.0.1:5173`. The console proxies `/api/v1` to `http://127.0.0.1:5180`. Local mode accepts loopback requests and defaults to the `local/dev/default` scope. **Settings** shows the current scope, storage, and registered capabilities.

### Load the screenshot fixture

A fresh workspace starts empty. To follow the screenshots, stop the default API if it is running. In one terminal, create the synthetic records and then start the API against the same database and assets:

```sh
fixture_root=$(mktemp -d)
AGENTCMD_OFFLINE_FIXTURE=1 AGENTCMD_OFFLINE_FIXTURE_ROOT="$fixture_root" \
  mise exec -- dotnet run \
  --project tests/fixtures/AgentCmd.ControlPlane.OfflineSeed/OfflineSeed.csproj -- --seed

mise exec -- dotnet run --project src/Zeeq.AgentCmd.ControlPlane.Host -- \
  --ControlPlane:LocalMode=true \
  --ControlPlane:DatabasePath="$fixture_root/management.db" \
  --ControlPlane:AssetPath="$fixture_root/assets" \
  --urls=http://127.0.0.1:5180
```

The fixture uses fake chat clients. It writes `incidentExecutionId` and `reassessmentJobId` to `$fixture_root/fixture-ids.json`. The synthetic incident has its own source family, separate from the fixture’s calibration cases. You will create a new **Regression** draft for it.

## Inspect the original execution

Open **Traces**, then open the row matching `incidentExecutionId`. Expand **Stored execution evidence** to inspect the output reference, retained value, and any attempt evidence. The fixture source says “The supported value is A.” The fake client returned `C`. The console lists records reported to the control plane. For full spans, use your configured trace collector.

## Capture a regression case

1. In **Datasets**, select **New draft dataset**. Name it **Extraction regression**, set the body to `{"purpose":"Regression","cases":[]}`, and select **Create draft dataset**.
2. Return to the execution. Under **Add to regression draft**, select the draft and enter a reason. Choose **Add to regression draft**.
3. Save the shown case ID. Use **Open review** to inspect the new review, or **Open draft** to return to the dataset. Repeating capture of the same execution into the same draft can reuse the case.

![Execution detail showing the captured incident case and its draft and review links.](/images/management-console/execution-capture.webp)

**Open draft** and **Open review** point to the case and its incident review.

The draft case contains the retained input and asset references. Its provenance links back to the execution and any recorded output reference. For production runs, the host must report authorized input evidence. Missing input, unavailable assets, or a withheld acceptance source can block capture.

## Review the case and record an expected answer

1. In **Review evidence**, inspect **Exact stored output reference** and **Stored output**. Select **Claim review**, then **Accept incident**. Acceptance admits the case to the draft. **Reference** still shows **None**.
2. Under **Datasets**, reopen the draft and select the case to inspect its input. In **Edit draft**, add a `reference` to that case in **Body JSON**. Preserve its existing input, assets, and provenance. The editor requires an explicit `exposed` boolean. Use `false` for this unmarked synthetic regression case.
3. Record `"reference": {"value": ["A"], "completeness": "Exhaustive"}` for this fixture because the source names only A. Choose **Save draft**.
4. Choose **Freeze…**, then **Freeze revision**. Record the dataset ID and frozen revision. Reopen it from **Datasets** or fetch it with `GET /api/v1/datasets/{id}`.

## Evaluate when you are ready

- **Replay selected inputs.** Create and freeze a benchmark for the frozen dataset. Define the business criteria and primary criterion. In **Experiments**, launch a backtest with that benchmark, the dataset, and the intended build and publication candidates. A compatible registered worker claims the job and runs the candidate. A replay creates new executions.
- **Reassess existing outputs.** Choose reassessment to apply judgment to exact original outputs. This skips candidate execution. A judge criterion can still require a separate model call. To grade one historical output, open its execution and use **Assess exact execution** with the applicable frozen criterion.
- **Read results.** Open the job in **Experiments** and inspect its pinned dataset, benchmark, execution and assessment evidence, and unresolved criteria. The screenshot shows a separate fixture job in `AwaitingAssessment`. It retains the original outputs and still needs assessment. It did not run the regression case created in this walkthrough.

![Seeded reassessment job showing the source job, pinned dataset and benchmark, and Awaiting Assessment state.](/images/management-console/reassessment-job.webp)

## Other console tasks

| Work area | Use it to |
| --- | --- |
| **Commands** | Inspect registered build manifests and command contracts. Draft and freeze a publication for a known build. |
| **Experiments** | Launch a backtest or reassessment, inspect jobs, and compare assessments and guardrails. |
| **Traces** | Inspect stored execution and attempt evidence, capture incidents, and request exact-output assessments. |
| **Datasets** | Curate cases, inspect source and reference coverage, and freeze dataset and benchmark definitions. |
| **Review** | Claim review work, assess recorded evidence, and inspect judge calibration results. |
| **Settings** | Verify the active scope, storage, and worker and publication capabilities. |

For HTTP calls, scope, revision checks, and worker integration, see the [management API reference](/reference/management-api).
