When you ask a model for an `Invoice`, two pieces need to agree: the schema sent to the model and the code that reads the JSON it returns. If they describe different shapes, the model can follow the schema and still produce a result your application cannot read.

For ordinary DTOs, AgentCmd generates the `System.Text.Json` metadata for both jobs during compilation. You write the input and result types; the generator discovers them from the command or composition. Requiredness and nullability are part of that same contract.

There is no precompiler executable or extra MSBuild import. Reflection fallback is not the default. Unsupported automatic shapes produce `AGENTMETA001` with a reason; they do not silently switch serializers.

## Supported automatic shapes

The bounded automatic path covers accessible classes and records, selected public constructors, required/init members, common scalar values, `Guid`, `DateOnly`, enums, nullable values, one-dimensional arrays, lists, string-key dictionaries and immutable arrays. A `byte[]` keeps STJ's base64 format. Supported attributes include property names, requiredness, selected ignore conditions and named derived types. Concrete, parameterless type-level `JsonConverter<T>` implementations are supported.

This is not every STJ feature. Extension data, property converter factories, advanced JSON policies and other unsupported shapes require an explicit context. The supported ignore conditions are `Always`, `Never`, `WhenWritingNull` and `WhenWritingDefault`.

## Choose an explicit context

For an exceptional contract, author an STJ context that declares **both** the command's parameter and result roots, then select it on the command. For example, you may want to keep JSON fields that were not known when the result type was written. This is a declaration excerpt; the host and invocation are the same as the quick start.

```csharp [ExplicitContext.cs]
using System.Text.Json;
using System.Text.Json.Serialization;
using Zeeq.AgentCmd;

namespace QuickStart;

public sealed record ExtraInput(string Document);

public sealed class ExtraResult
{
    public string Name { get; init; } = "";

    // Keep unknown fields rather than dropping them on read.
    [JsonExtensionData]
    public Dictionary<string, JsonElement> Extra { get; init; } = new();
}

// The explicit context needs both ends of this command.
[JsonSerializable(typeof(ExtraInput))]
[JsonSerializable(typeof(ExtraResult))]
public partial class ExtraJsonContext : JsonSerializerContext;

// Tell AgentCmd to use this context for the exceptional shape.
[PromptCommand("extra.extract", JsonContext = typeof(ExtraJsonContext))]
public sealed partial class ExtractExtra : PromptCommand<ExtraInput, ExtraResult>
{
    const string UserTemplate = "Extract a name from {Document}.";
}
```

A composite can select its whole context with `CompositeOutput.JsonContext`; that context must declare the whole root. An authored context retains its naming, converter and unmapped-member options. Generated validation still applies to the command. Attribute-declared concrete converters get separate instances per metadata scope; generated provenance supports compatible composition without sharing mutable converter state.

## What the native proof covers

A local NuGet-only consumer was published and executed as a macOS ARM64 NativeAOT binary with JSON reflection disabled. It exercised a generated command, MEAI helpers and middleware, cross-assembly composition, exact stored-whole readback and grading, an explicit context, and provider/telemetry integration using fake data.

That proof is specific to the tested runtime and synthetic client. It is not a blanket NativeAOT claim for every operating system or vendor SDK. Other runtime IDs and SDK bridges need their own executed checks. The native toolchain emitted debug-artifact warnings; they were not IL/trimming warnings and were not suppressed.
