You've written a command that extracts an invoice. It works, but you wonder whether a shorter prompt or a different model would handle messy invoices better. Rebuilding and redeploying the application for every idea makes that a slow question to answer.

An experiment lets the application keep calling the same command while a source supplies a new prompt and settings. The command still owns its input and output types. LlmCmd records which version ran and stores the result with the evidence you need to evaluate it later.

The [offline example](https://github.com/zeeq-ai/zeeq-llmcmd/tree/main/examples/Zeeq.LlmCmd.ExperimentsExample) writes a publication to a file, runs a primary and a shadow, and then changes the publication while the same process is running. It uses synthetic clients and needs no credentials:

```sh
mise run demo:experiments
```

## A/B or shadow?

These are two useful ways to ask different questions:

- **A/B:** assign each input to one variant. The chosen variant runs and its result goes back to the caller. The optional weighted selector can keep an assignment stable for a host-provided unit, such as an account.
- **Shadow:** run a comparison variant alongside the primary. The caller receives only the primary result. The shadow has its own run and stored output; a slow or failed shadow does not replace the primary.

For example, you might send half of accounts to the existing prompt and half to a shorter prompt. Before exposing the shorter prompt, you could instead run it as a shadow on a small share of traffic and compare its stored outputs. Both approaches make additional model calls when you run more than one variant, so set an explicit budget and sampling policy.

## What can change?

A source publishes one versioned snapshot containing the variants for a partition. A variant can supply a system or user template, permitted parameter overrides, and a route to a host-registered client and model. The route can also set supported sampling defaults such as temperature and top-p.

The source cannot create a client, install an SDK, supply credentials, or change the generated output contract. Your host registers the clients and decides which model routes and settings are allowed. A model-bound client can only use its configured model or deployment. A per-request client can select another allowed model without adding a static profile.

`RoutePolicy` sees each route in the fallback chain with its effective temperature, including an explicit invocation override. It must authorize the actor, target and supplied settings. An unsupported route uses the configured default before a provider send. The current file source supports temperature, maximum output tokens, top-p and top-k; it rejects unknown fields. Explicitly clearing an inherited sampling value is not yet supported.

An override changes a real parameter value, so the command author must opt in to each field. For example:

```csharp [InvoiceRequest.cs]
using Zeeq.LlmCmd;

namespace InvoiceDemo;

public sealed record InvoiceRequest(
    string Document,
    [property: RuntimeOverride] string Locale = "en"
);
```

Here an experiment can try another `Locale`, but it cannot replace `Document`. Keep user-provided content and other sensitive inputs out of the override set. The first implementation supports scalar positional properties on a sealed record whose complete state has a safely generated snapshot. Other opted-in shapes produce a generator diagnostic. Template-only changes can use the existing scalar placeholders without making the caller's whole input overridable.

Overrides are applied to the typed input before validation and rendering. An invalid external release uses the complete configured default before a provider call. LlmCmd does not keep half of the treatment and half of the default.

## Versions and assignments

There are three identities to keep straight:

- The **command contract** describes the compiled input and output shapes. `command.ExperimentContract` exposes its ID, revision and generated signature to a host or control plane.
- A **snapshot revision** identifies an immutable publication from your source. Publish a new revision when its contents change.
- A **variant ID** identifies one choice within that snapshot. Its experiment ID, variant ID and revision travel with the stored result.

The command contract prevents a release written for an older shape from being applied to a different one. The snapshot revision tells an evaluator which publication supplied the prompt and route. The variant tells the evaluator which choice ran within that publication.

The optional `WeightedExperimentSelector` assigns a stable host-provided unit to a variant according to its weight. Without a selector, the source's control variant runs. The host chooses what a unit means; a trace ID is useful for correlation but is not an authorization or assignment policy.

When several commands in a composition share an experiment ID, the selector chooses an arm once for that experiment. Each command keeps its own template and route for that arm. Their variant IDs, weights and control ID must agree; an incompatible group uses the configured defaults for that group.

## Keep a running call consistent

The optional process-local cache gives the latest snapshot a short absolute lifetime. Its default is 30 seconds. An update becomes visible on a later lookup after the cache expires; it does not change a call that has already selected a snapshot. A host can supply another source or caching strategy through the source interface.

`FileExperimentSnapshotSource` reads a versioned JSON file. `CachedExperimentSnapshotSource` wraps a source with a bounded, single-flight in-memory cache. This cache is process-local; nodes can observe an update at different times. The file source serves its current publication, so a host that needs historical revisions must retain them separately. Publish a file update atomically, such as by writing a temporary file and renaming it, so readers do not see a partially written publication.

The offline example wires those pieces like this:

```csharp [Source setup]
var cache = new ExperimentSnapshotCache(
    new ExperimentCacheOptions
    {
        LatestDefinitionLifetime = TimeSpan.FromMilliseconds(100),
    }
);
var source = new CachedExperimentSnapshotSource(
    "invoice-file",
    new FileExperimentSnapshotSource(path),
    cache
);
var resolver = new ExperimentResolver(
    source,
    selector: new WeightedExperimentSelector()
);
```

Pass the resolver and host policies to `UseExperiments`. Its factory overload receives the service provider, so shadow workers can obtain an `IServiceScopeFactory` without creating a second provider. The example uses a short cache lifetime to make its update visible quickly; choose a lifetime that fits your application.

If the external source times out, is unavailable, or returns an invalid release, a new call uses the complete locally configured default and records a reason. Caller cancellation still cancels the call. A source failure does not grant access to a run or bypass actor authorization.

A composition pins one snapshot and its choices before it claims a part. Deferred `Then` steps use that same snapshot, even if the source changes after an earlier step. A retried draft stays on its pinned version. Start a new draft or trial when you want to evaluate a new version. For a configured-default pin, the host must supply a stable default-configuration fingerprint and keep the corresponding defaults available for replay.

## Keep comparison results useful

For an experiment-enabled command, the stored output includes experiment evidence: the effective templates and parameters, their origins, the selected version and variant, and routing information. Attempt records identify the route and portable settings used for each provider attempt. An explicit invocation profile or temperature can take precedence over experiment settings, so inspect the effective evidence rather than assuming the source's request was sent unchanged.

For a shadow, the host can observe a result containing the comparison group, variant and exact stored `OutputRef`. Use that reference to read and grade the shadow output. The observer is best effort; use a host-owned durable store when losing a comparison record on restart is unacceptable. The default ledger and scheduler are in memory.

Only run shadows through host-approved pipelines and data destinations. A tool call or other side effect could otherwise happen more than once. The host owns sampling, concurrency, queue capacity, timeouts and cost controls. Unknown usage or prices do not establish a hard spend limit.

For a composition, grade the exact stored whole. Its member lineage points to the exact component outputs, including explicitly reused parts. A component execution ID or trace is not a substitute for the whole's `OutputRef`. See [Evaluate the stored whole](/guides/evaluation) and [Telemetry and evaluation capture](/guides/accounting-and-observability).

## Shadow a composition

In a composition, one part may depend on another. `CompositionShadowCoordinator` runs a separate composition with its own draft and trial. Its parts use the primary's pinned publication and the shadow variants the host selects. They never attach to the primary draft.

The host registers an `ICompositionShadowFactory<TWhole>` to build the shadow from a frozen JSON payload and an `ICompositionShadowPolicy` to authorize the work. Once the primary draft has a pin, the host offers the shadow to a bounded scheduler. The variant map names a variant for each command in the pinned publication; commands in the same experiment use the same arm. A host selector must supply the comparison-group ID on the primary's assignments so the coordinator can link the primary and shadow compositions.

```csharp [Offer a composition shadow]
// The host obtained these values from the authorized primary and its publication.
var accepted = await coordinator.TryScheduleAsync<DocumentExtraction>(
    primaryDraftId,
    actor,
    frozenPayload,
    variantsByCommand,
    comparisonGroupId,
    cancellationToken
);
```

`accepted` means the scheduler admitted the work; it does not mean the shadow has finished. The coordinator's result observer receives the shadow's exact aggregate `OutputRef` only after publication and ledger readback. Use that reference to evaluate the shadow composition. An in-memory scheduler can lose accepted work on restart, and its timeouts require work to honor cancellation. The [composition tests](https://github.com/zeeq-ai/zeeq-llmcmd/blob/main/tests/LlmCmd.Composition.Tests/ExperimentCompositionTests.cs) show a factory, policy, independent drafts and aggregate grading.
