You have a prompt in production and want to try a different one. Can you change it without rebuilding the application, keep the caller's result separate, and find the comparison output afterward?

This example does all three with a local file and two synthetic clients. It does not need a provider account or credentials.

```sh
mise run demo:experiments
```

You can read the complete [command](https://github.com/zeeq-ai/zeeq-llmcmd/blob/main/examples/Zeeq.AgentCmd.ExperimentsExample/InvoiceCommand.cs) and [program](https://github.com/zeeq-ai/zeeq-llmcmd/blob/main/examples/Zeeq.AgentCmd.ExperimentsExample/Program.cs) in the repository. The program creates and deletes its own temporary file.

## Give the experiment one knob

The input contains the invoice document and a locale. The command author marks only the locale as overridable:

```csharp [InvoiceCommand.cs]
public sealed record InvoiceInput(
    string Document,
    [property: RuntimeOverride] string Locale = "en"
);
```

The source can try `fr` for `Locale`; it cannot replace the caller's `Document`. The generated binding applies that override to the typed input before validation and rendering.

## Publish and compare

The program obtains the command's `ExperimentContract` and writes its ID, revision and signature into the file. That ties the publication to the input and output shapes it was prepared for. In the first publication, the control has all of the A/B weight. The candidate runs as a shadow.

The candidate changes the template to `Compare {Document} in {Locale}.`, sets `Locale` to `fr`, and selects the synthetic alternative client with a different model and temperature. The host's route and shadow policies explicitly allow this demonstration. In a real application, those policies should allow only the destinations, models and side effects you intend to test.

After the first call, the program waits for the shadow result. The observer supplies the shadow's `OutputRef`, so the program can read the exact stored output and inspect its experiment evidence. The primary and shadow share a comparison-group ID but have separate runs and outputs.

## Update without a restart

The program writes a second revision with the weights reversed. After the short demo cache lifetime, the next call selects the candidate as its primary and runs the control as a shadow. It checks the effective prompt, model, temperature, revision and stored shadow output.

The example sets a 100 ms cache lifetime to keep the walkthrough quick. The default is 30 seconds. The file source serves its current publication; a production source can retain older revisions and use a different cache. See [Runtime experiments](/guides/runtime-experiments) for fallback, composition and storage behavior.
