A support queue needs to route each request to the right team. A model can suggest a category, but what happens if it returns an unexpected label—or the provider times out? Treating either case as `billing` could send a customer down the wrong path.

This command makes the expected labels explicit and leaves failures for the host to handle. It does not decide the application's fallback policy for you.

This is an **illustrative application**, not a runnable sample in the repository. It uses the same declaration and execution APIs as the offline invoice example.

## Define the task once

```csharp [SupportCommand.cs]
using Zeeq.LlmCmd;

namespace SupportDemo;

public sealed record SupportInput(string Message);

public sealed record SupportLabel(string Category);

public sealed partial class ClassifySupport
    : PromptCommand<SupportInput, SupportLabel>, IResultValidator<SupportLabel>
{
    const string Id = "support.classify";
    const string UserTemplate =
        "Classify this support request as billing, technical, or other: {Message}";

    // Valid JSON is not enough if the category is outside our vocabulary.
    public static string? ValidateResult(SupportLabel result) =>
        result.Category is "billing" or "technical" or "other"
            ? null
            : "Unknown support category";
}
```

The result hook rejects a category outside the three values. Generated serializer metadata also rejects missing required fields. Neither check proves the model chose the right category; evaluate that separately against labeled examples.

## Host and invoke

Register the host's keyed `IChatClient` pipeline as `support` first. In this setup excerpt, `services`, `model` and `actor` are supplied by the host; `model` is its configured model or deployment ID and `actor` comes from a trusted boundary.

```csharp [Host setup]
// The keyed client is host-owned; the profile gives the route a name.
services
    .AddLlmCmd(options =>
        options
            .AddChatClient("support", serviceKey: "support")
            .AddProfile("support-route", "support", model)
            .UseDefaultProfile("support-route")
            .UseActor(_ => actor)
    )
    .AddGeneratedCommands();
```

Resolve `ClassifySupport` from DI. Each call uses its own immutable parameters. This excerpt returns the library outcome to the host so the host decides what to do with a failure.

```csharp [Application code]
static Task<Outcome<SupportLabel>> ClassifyAsync(
    ClassifySupport command,
    string message,
    CancellationToken cancellationToken
)
{
    return command
        .WithParameters(new SupportInput(message))
        .ExecuteAsync(cancellationToken);
}

var outcome = await ClassifyAsync(command, message, cancellationToken);

// The application chooses what to do with each case.
if (outcome is Outcome<SupportLabel>.Success success)
{
    Console.WriteLine(success.Value.Category);
}
else if (outcome is Outcome<SupportLabel>.Failed failed)
{
    Console.WriteLine($"Classification failed: {failed.Failure.Kind}");
}
```

A success includes a delivery receipt; inspect it when later work requires a stored output. A failure may represent invalid input or output, provider failure, configuration failure, a hook failure or cancellation. Do not convert it to a default category without an explicit product policy. Treat prompts and captured parameters as potentially sensitive; configure storage and observation accordingly.

For runnable equivalents, see the [invoice example](https://github.com/zeeq-ai/zeeq-llmcmd/tree/main/examples/Zeeq.LlmCmd.CommandExample) and [generated-boundary tests](https://github.com/zeeq-ai/zeeq-llmcmd/blob/main/tests/LlmCmd.CommandRoot.Tests/GeneratedBoundaryTests.cs).
