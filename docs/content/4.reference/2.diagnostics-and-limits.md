The generator can catch some mistakes before a request ever reaches a model. For example, a profile can name a client that was never registered, or a DTO can use a JSON shape the automatic serializer does not support.

The table below is a starting point when you see a diagnostic. Runtime configuration, authority, stored references, and provider behavior still need their own checks.

| Diagnostic | What to inspect |
| --- | --- |
| `LLMCMD001` | The command or composition declaration and the diagnostic message: for example, a missing identity, an invalid template or a declared setting that is not a non-null constant of the expected type. |
| `LLMCMD002` | A static string member resembles `UserTemplate` or `SystemTemplate` but would not be used as that template. |
| `LLMPROFILE001` | The partial profile catalog and its declared IDs. |
| `LLMMETA001` | The DTO shape, constructor, attribute or converter that automatic metadata cannot safely represent. |
| `LLMCLIENT001` | A named profile's client argument does not match a known registered client in the analyzed setup. |
| `LLMCLIENT002` | A client name is registered twice in the same analyzed setup. |
| `LLMCLIENT003` | A constant profile model conflicts with the registered client's constant `fixedModel`. |

Client names are case-sensitive. For direct `AddLlmCmd` lambdas the analyzer understands straight-line builder calls and fluent chains, including constants, concatenation and `nameof`. It collects registrations before checking profiles, so a profile can appear first. Branches, loops, aliases, builder escapes and unknown registration names make the setup open; the analyzer avoids speculative errors. A dynamic profile client skips that route, and a dynamic model skips its model comparison. Argument helpers that do not receive or capture the builder do not change declared registration membership; diagnostics assume argument evaluation completes.

Command declaration names are case-sensitive. `LLMCMD002` is a warning for close template-name typos and a few common alternative names, only when the corresponding exact declaration is absent. It does not infer the intent of arbitrary methods or instance data. Use `UserTemplate` for the user-role message and optional `SystemTemplate` for the system-role message; both use the same typed input.

## Serializer boundary

Automatic STJ metadata covers ordinary supported DTOs without `[JsonSerializable]` markup or a separate precompile tool. Schema, serialization and deserialization share that contract. Unsupported shapes produce `LLMMETA001`; an explicit `JsonSerializerContext` is the extension point for contracts outside the automatic boundary.

Common supported shapes include accessible records and classes, selected public constructors, required and init members, common scalars, `Guid`, `DateOnly`, enums, nullable values, one-dimensional arrays, lists, string-keyed dictionaries and immutable arrays. Supported attributes include JSON property names, requiredness, several ignore conditions, named derived types and concrete parameterless type-level converters. Advanced JSON policies, property converter factories and extension data require an authored context. Conflicting nullable instantiations of a generic DTO may also require an explicit context.

Declare an authored partial `JsonSerializerContext`, register its relevant roots with `[JsonSerializable]`, and select it with `PromptCommand.JsonContext` or `CompositeOutput.JsonContext`. Its options own naming and converter policy; generated validation still applies. Options or converter instances that cannot be proven compatible can be rejected when composing parts.

## NativeAOT and package scope

The core, Providers and OpenTelemetry libraries are checked for AOT compatibility. The package-only test publishes and runs a macOS ARM64 native executable with JSON reflection disabled. It exercises synthetic command execution, composition and exact stored-whole evaluation, explicit context, MEAI helpers, provider extraction, telemetry and propagation. The core package has no precompiler tool or consumer build target.

That is evidence for the tested runtime, toolchain and paths. It does not establish NativeAOT support for every runtime ID or vendor SDK. An external SDK bridge needs its own compatibility proof. The pinned SDK and C# version are in `global.json`; follow the repository's `mise` setup. The packages are currently local alpha artifacts, not a claim that they are published to nuget.org.

The native toolchain can emit SDK debug-map and Swift/Foundation debug-artifact warnings. These are separate from IL/trimming warnings; no warning is suppressed. See `docs/architecture/serialization-and-aot.md` in the repository for the detailed boundary.

## Runtime and storage limits

- The default feedback ledger and composition store are in memory. They are not durable recovery, cross-process leases or exactly-once billing.
- A run or correlation ID is not authorization. Supply a trusted actor and independently authorize access to stored outputs.
- Reusing a part requires a readable, compatible stored reference in the permitted run. Grade the aggregate's own `OutputRef` when evaluating the whole.
- Missing usage and prices are unknown, not zero. Pricing is an estimate under a stated scope, not a provider invoice.
- Native streaming and some provider Responses paths are incomplete. Consult provider contract tests before claiming support for a protocol.

Run `mise run verify` for the offline repository gate. Live API and container-dependent checks are separately opt-in; they are not needed for the examples on this site.
