## Why use AgentCmd?

Imagine an application that reads an invoice and asks a model to extract its total. The first version may be a prompt and a call to a chat client. Then an invoice comes back with the wrong total, and someone asks a few reasonable questions:

- Which prompt and input produced this result?
- Which model was used, and did the call get retried?
- Can we read and evaluate the exact result that was stored?

Those questions get harder when the prompt, its inputs, the model call, and the result live in different helpers. For a document assembled from several calls, there is one more question: **which result is the whole invoice?** A trace of the last call is not the invoice the application uses.

AgentCmd gives that operation a home. Think of a command as a small recipe: it names the prompt, describes the input and output, and knows how to run through your chat client. Afterward, you can inspect its captured user prompt, inputs, and result. You can also compose several commands into one result and grade the finished document.

Microsoft.Extensions.AI (MEAI) already offers typed responses, JSON schema helpers, and middleware. AgentCmd builds on those APIs. It adds the command identity, captured inputs, a storage receipt (did the ledger accept the output?), and composition and grading around them.

Here is the same operation written directly against `IChatClient`. It returns the same typed `Invoice` and keeps the same audit data. This sketch is illustrative:

```csharp [Without AgentCmd]
// The application owns the prompt text, the schema, the parsing, and the audit trail.
var prompt = $"Extract the invoice from {document}.";
var response = await chatClient.GetResponseAsync<Invoice>(prompt, cancellationToken: ct);

if (!response.TryGetResult(out var invoice))
{
    // Decide what a bad parse means, and log which prompt and input caused it.
    return Failure("invoice.extract", prompt, document);
}

// Store the prompt, the input, and the result so someone can grade them later.
await audit.SaveAsync("invoice.extract", prompt, document, invoice, ct);
```


That is reasonable for one call. When the operation is reused, observed, and graded across an application, every copy has to keep the prompt ID, the input, and the audit record in sync. With AgentCmd, the declaration keeps them together. Both versions call the same `IChatClient`.

```csharp [ExtractInvoice.cs] {5,7-8}
public sealed record InvoiceInput(string Document);

public sealed record Invoice(decimal Total, string Currency);

public sealed partial class ExtractInvoice : PromptCommand<InvoiceInput, Invoice>
{
    const string Id = "invoice.extract"; // Stable even if the class is renamed.
    const string UserTemplate = "Extract the invoice from {Document}.";
}
```

```csharp [Call site] {2-3}
var result = await extractInvoice
    .WithParameters(new InvoiceInput(document)) // Supply this invocation's input.
    .ExecuteAsync(ct); // The model call happens here.
```

The generator supplies the schema, serializer metadata, and registration. `result` contains a typed outcome and, when available, the captured prompt and parameters. The call site above assumes an injected command, a document, and a cancellation token. The [quick start](/getting-started/quick-start) builds the complete example with an offline client.

## Why a command?

AgentCmd borrows a useful idea from `SqlCommand`: give a string-based operation an identity, parameters, execution, and a result. It is a familiar way to put the parts of an operation in one place.

The analogy has limits. Model output is not deterministic, and a prompt is not a SQL transaction. A typed result still needs validation. A provider call can fail, or incur cost after you cancel it.

The library extends [Microsoft.Extensions.AI](https://learn.microsoft.com/en-us/dotnet/ai/microsoft-extensions-ai) (MEAI). You supply an `IChatClient`; its middleware can still handle retries, caching, tools, and telemetry. AgentCmd adds a typed command and execution contract around that pipeline. It creates command and routing activities during execution. Optional provider extraction and OpenTelemetry packages let the host capture attempts and select an exporter without coupling a provider to a collector.

## Working with coding agents

A command keeps its stable ID, prompt template, and input and output types in one declaration, so an agent has one file to read and change. The generator reports contract errors at build time, which gives the agent quick feedback. Point an agent at [`llms.txt`](/llms.txt) and the [API cheat sheet](/reference/api-cheat-sheet) to get started.

## Where it helps

- **Extract one structured result:** keep an invoice prompt and its input/output contract together, then inspect a typed outcome.
- **Use several clients:** route an extraction and a review to separate client pipelines and model profiles.
- **Observe and evaluate a run:** capture provider attempts, inspect prompt inputs, and read the exact stored output for a grade.
- **Assemble one document:** extract a header, parties and lines separately; run a totals step using the stored line result; grade the exact published invoice.

Use a direct `IChatClient` call, including MEAI's typed-response helpers, when it meets your needs without AgentCmd's command identity, capture, storage receipts, or composed results. AgentCmd does not make a provider deterministic or supply a durable ledger by default.

::note
This is the one limit that changes a design decision. See [Diagnostics and limits](/reference/diagnostics-and-limits) for the rest. The default ledger and composition store are in memory. They do not provide process-restart recovery, distributed leases, or exactly-once provider billing.
::
