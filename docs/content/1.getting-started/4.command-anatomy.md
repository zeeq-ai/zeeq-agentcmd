Suppose several parts of your application need to extract an invoice. You could repeat the prompt and parsing rules at each call site, but then a change has several places to find. A command gives that operation one name and one home.

The declaration below describes **what** the command accepts and returns. The generator supplies the routine rendering, schema, serializer metadata, and registration around it.

```csharp [ExtractInvoice.cs]
using Zeeq.LlmCmd;

namespace QuickStart;

public sealed record InvoiceInput(string Document, string Locale = "en");

public sealed record Invoice(decimal Total, string Currency, int Count = 3);

public sealed partial class ExtractInvoice
    : PromptCommand<InvoiceInput, Invoice>,
      IInputValidator<InvoiceInput>,
      IResultValidator<Invoice>
{
    const string Id = "invoice.extract"; // Identity for captures and evaluation.
    const string UserTemplate = "Extract an invoice from {Document} ({Locale}).";

    // Reject a missing document before calling the provider.
    public static string? ValidateInput(InvoiceInput input)
    {
        return string.IsNullOrWhiteSpace(input.Document)
            ? "Document is required"
            : null;
    }

    // A JSON number can be valid JSON and still be an invalid invoice total.
    public static string? ValidateResult(Invoice result)
    {
        return result.Total < 0 ? "Total cannot be negative" : null;
    }

    // The host or invocation can choose a different setting later.
    static partial void ConfigureDefaults(ChatSettingsPatch defaults)
    {
        defaults.Temperature = 0.2f;
    }
}
```

`Id` and `UserTemplate` are constants; `SystemTemplate` and `Profile` are optional constants. The placeholder name refers to a public input property. A bad or ignored placeholder fails generation. Keep the ID stable when changing code names; increment a prompt revision when the authored definition changes as appropriate for your application.

`Count` has a constructor default, so an absent value keeps `3`; it is not made required merely because it exists. Required members and nullability are represented in the generated contract. Nested validation also checks collection elements where applicable.

Declare `IInputValidator<T>` or `IResultValidator<T>` directly on the command to opt into each validation hook. The compiler requires a matching static method for each declared interface, so a misspelled or missing method fails the build. Use a public static method as above, or an explicit static interface implementation to keep the hook out of the command's public members. The generator checks that each interface uses the command's corresponding type and rejects competing hooks for the same phase.

The generated structural checks run before the authored hook. A hook returns `null` for success or a reason for failure. Keep hooks synchronous, deterministic, and free of side effects: composition, experiments and shadows can validate inputs more than once. Direct generic calls to the interface invoke only the authored hook; command execution also performs its generated structural checks.

Existing private static `ValidateInput(T)`, `ValidateResult(T)` and overloaded `Validate(T)` hooks remain supported. They are discovered by exact name, so a misspelled legacy method is not recognized. A thrown hook on a direct call returns `HookFailure`. If a composition detects an input hook exception before a leaf runs, it reports `hook_failure:ValidateInput` without sending that part. `ConfigureDefaults` supplies command-level defaults. Profile settings and explicit invocation settings can override defaults; see [Profiles and clients](/guides/profiles-and-clients).

::note
A configured invocation is a value you can branch from. Calling `WithProfile`, `WithTemperature` or `Configure` returns another invocation; work begins at `ExecuteAsync`.
::

The example uses plain DTOs. For attributes, unsupported shapes and explicit serializer contexts, see [Serialization and NativeAOT](/guides/serialization-and-nativeaot).
