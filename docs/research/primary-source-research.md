# LlmCmd primary-source research

Verified on 2026-11-01. This document reports source findings and separates them from proposed LlmCmd behavior. No live model requests were required.

## Version and scope

The final requested target is **C# 15 / .NET 11**. The initial C# 11 constraint has been superseded. The inspected MEAI baseline remains **Microsoft.Extensions.AI 10.11.0**. Consuming that package from a newer target framework does not require changing its version.

- Microsoft.Extensions.AI 10.11.0 is the current stable package observed on NuGet, published 2026-10-14. Its official release is [v10.11.0](https://github.com/dotnet/extensions/releases/tag/v10.11.0).
- Source was read at the release commit **25f07afa51034e37b334210642d7dc5f191c142d**, rather than assuming that GitHub `main` or an API proposal matches the package.
- The live NuGet flat-container indexes returned **10.11.0** for [Evaluation](https://api.nuget.org/v3-flatcontainer/microsoft.extensions.ai.evaluation/index.json) and [Evaluation.Reporting](https://api.nuget.org/v3-flatcontainer/microsoft.extensions.ai.evaluation.reporting/index.json). [Evaluation.NLP](https://api.nuget.org/v3-flatcontainer/microsoft.extensions.ai.evaluation.nlp/index.json) returned **10.11.0-preview.1.26513.7**. Do not assume that every Evaluation package has the same stability designation.
- .NET 11 SDK availability, its exact RC/GA build, and compilation under the revised language target are owned by the integration spike. This research did not independently verify those environment facts.
- The exact requested reference is **[CharlieDigital/SKPromptGenerator](https://github.com/CharlieDigital/SKPromptGenerator)**. Its current source and package version are **0.5.1**, at commit **cfb1bc1d0f2851821d3e66575ee52392d2609382**, dated 2025-08-30.

## Recommendation

Build a small command contract and source generator above MEAI. Reuse MEAI for provider abstraction, middleware composition, function invocation, response aggregation, telemetry, and evaluation. Reuse SKPromptGenerator's authoring idea and typed-token examples. Its generated execution model needs substantial replacement for this design.

LlmCmd must add stable command identity, revisions, separate raw templates and typed values, runtime override validation, caller metadata, a replayable execution record, and explicit expected-error results. These are application-level concerns that the inspected MEAI abstractions do not supply as a prompt-command contract.

## SKPromptGenerator: actual generation contract

The following findings come from the pinned implementation, rather than the README alone:

- [PromptSyntaxReceiver.cs](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/generator/PromptSyntaxReceiver.cs) accepts attributed `const string` fields. Although the generated attribute permits properties, this receiver only visits field declarations. It reads the constant through Roslyn and derives the output class name from the field name.
- [PromptGenerator.cs](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/generator/PromptGenerator.cs) recognizes tokens such as `{{$country}}` and `{{$count:int}}`. Unannotated parameters become `string`. Repeated names become one constructor argument. Type annotations are inserted as C# type text; this is not a separate runtime parameter schema.
- Each field produces a partial `<FieldName>Prompt` class. Its constructor requires every discovered parameter. This gives compile-time enforcement of argument presence and declared C# types. It does not provide a staged fluent builder, runtime null/value validation, or enforcement for parameters introduced by a later external template.
- Its `Text` property is a generated interpolated string. Values become formatted text when that property is evaluated. It does not expose the raw template and named typed values as a separate execution descriptor.
- Its `Settings` property creates `OpenAIPromptExecutionSettings`. [PromptTmpl.cs](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/generator/PromptTmpl.cs) supplies defaults of 500 maximum tokens, temperature 0.5, and top-p 0.
- [PromptTemplateBase.cs](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/generator/PromptTemplateBase.cs) resolves an SK `IChatCompletionService` from a `Kernel`, optionally by service ID. It builds history, appends the formatted prompt as a user message, and returns response text. JSON methods remove Markdown fences and deserialize, optionally returning the JSON string as well. They do not preserve MEAI response metadata or return a closed expected-error hierarchy.
- [PromptTemplateAttribute.cs](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/generator/PromptTemplateAttribute.cs) allows a custom base type. This is an extension point, but the generated settings and imports remain coupled to SK/OpenAI.
- The generator and its generated attributes use class primary constructors. These would have blocked the original C# 11 target. They are not a language blocker under the revised C# 15 target. The architectural gaps above still apply. The [generator project](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/generator/SKPromptGenerator.csproj) itself targets .NET 8 and Roslyn 4.8.0; compatibility with a new compiler host should be tested before taking a dependency.

Reuse candidates: attributed literal prompts, token-to-parameter extraction, repeated-token examples, custom type examples, and generation tests. New work: a semantic incremental generator, diagnostics, namespace-safe generated names, template/parameter metadata, a MEAI executor, overrides, staged APIs if selected, and a collector.

The receiver uses syntactic attribute-name matching and only the first attribute in the first list. The generator deduplicates parameters by name without explicitly diagnosing conflicting type annotations. A production implementation should validate these cases through semantic symbols and explicit diagnostics. The existing [tests](https://github.com/CharlieDigital/SKPromptGenerator/blob/cfb1bc1d0f2851821d3e66575ee52392d2609382/tests/BasicTests.cs) demonstrate interpolation and typed arguments, but do not establish these stronger guarantees.

## MEAI execution and middleware

MEAI's `IChatClient` accepts message history, optional `ChatOptions`, and cancellation. The complete result is a `ChatResponse`; streaming returns `IAsyncEnumerable<ChatResponseUpdate>`. Keeping those objects in the executor preserves information that flattening the response to text would lose. See the pinned [interface](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Abstractions/ChatCompletion/IChatClient.cs).

[ChatClientBuilder](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/ChatClientBuilder.cs) supports wrapper factories, service-provider-aware factories, and anonymous delegates. **The first `Use` registration is the outermost wrapper.** A shared delegate can handle pre/post processing for both execution modes. To inspect or alter results, use the separate response/stream delegates or a `DelegatingChatClient`. Supplying only the complete-response delegate makes the streaming path operate on a buffered result. A collector that promises streaming should implement the streaming path explicitly.

[ChatOptions.Clone](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Abstractions/ChatCompletion/ChatOptions.cs) creates new collections for tools, stop sequences, and additional properties, but their contained references remain shared. Provider-specific `RawRepresentationFactory` must return a new native options object per call. Consequently, cloning is useful for request isolation but is not an immutable replay snapshot.

[ConfigureOptions](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/ConfigureOptionsChatClientBuilderExtensions.cs) receives a clone of caller options, or a new instance. The callback can apply defaults or overwrite values. **LlmCmd must define precedence itself.** A reasonable policy is application defaults, then command defaults, then a versioned runtime configuration, then explicit call overrides. Route-owned provider settings may need to override incompatible request settings after selection; record the final effective options too.

`ChatOptions.ModelId` is a model request, not a provider-selection mechanism. Select a configured provider/client through the executor's registry or a router. Record requested route/model separately from the returned model. Actual model-override behavior is adapter-specific: the inspected [OpenAI chat adapter](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.OpenAI/OpenAIChatClient.cs) patches the model when unset, while the [Responses adapter](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.OpenAI/OpenAIResponsesChatClient.cs) uses native options first, then `ChatOptions.ModelId`, then its configured default. Do not claim universal precedence for all providers.

### Current routing and failover

The following APIs are available in 10.11.0 but remain **experimental under MEAI001**:

- [RoutingChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Abstractions/ChatRouting/RoutingChatClient.cs) is a one-shot selector in the abstractions package. `Create` accepts an asynchronous selection callback. Selected clients remain caller-owned. Its `GetService` does not expose metadata from an unknown future selected client. Per-route wrappers are therefore better than treating a router's metadata as the actual provider.
- [FailoverChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatRouting/FailoverChatClient.cs) supplies invocation and attempt tracking. The shipped hook is `OnRoutingUpdateAsync(context, attempt, isTerminal, cancellationToken)`, not the different hooks in the original API proposal. The maximum-attempt property defaults to null. A custom policy must terminate or set an explicit bound.
- [OrderedFailoverChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatRouting/OrderedFailoverChatClient.cs) tries its snapshotted list in order and rethrows the last failure when exhausted. It owns clients unless `leaveOpen` is true.
- [SemanticRoutingChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatRouting/SemanticRoutingChatClient.cs) is an optional embedding-based router. Deterministic command/provider/model routing does not require semantic selection.

Failover permits another selection only after a failure before streaming output is committed and while request cancellation has not been requested. Once any update reaches the caller, a later failure is propagated. Enumerators must be disposed to release inner resources and report terminal state. The attempt hook can itself throw and replace the original outcome. Application emitters should therefore isolate optional telemetry failures instead of letting those failures change a successful model result.

### Caching and function invocation

[CachingChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/CachingChatClient.cs) caches completed results, not in-flight work. Concurrent misses can issue duplicate requests. A streaming response is written only after full enumeration. Streaming updates are coalesced by default, so a cache hit does not reproduce original chunk boundaries or timing. Failed or abandoned enumerations do not reach that final cache write.

[DistributedCachingChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/DistributedCachingChatClient.cs) serializes messages/options and additional values for its key. Keys are not guaranteed stable across package releases. Native `RawRepresentation` is not retained, and arbitrary additional-property values can return as `JsonElement`. The default writes do not specify an explicit expiration. Tools and native option factories also cannot be treated as a complete serialized identity merely by serializing `ChatOptions`.

Inference for LlmCmd: resolve template and parameter overrides before response-cache lookup. Include explicit route/configuration/tool revisions in the key where the normal serialized request omits them. Cache hits must be distinguishable from provider calls when calculating new spend. A response cache and a Redis prompt/configuration provider solve different problems.

[FunctionInvokingChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/FunctionInvokingChatClient.cs) runs a model/tool/model loop. One command can cause several provider calls. It supports iteration/error bounds, serial or concurrent invocation, and a function invoker hook. Complete-response execution aggregates reported usage across turns; streaming forwards updates and tool results that must be aggregated by the consumer.

Place the command collector outside that loop for one logical command record. Place provider-attempt telemetry inside it when per-call usage and model identity are needed. A cache outside function invocation can bypass tool work on a hit; a cache inside the loop caches individual model turns. Select order deliberately, especially for tools with external effects. Do not sum both a loop's aggregated usage and its child call usage into the same cost total.

## Telemetry, cost, and durable execution records

[UseOpenTelemetry](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/OpenTelemetryChatClientBuilderExtensions.cs) adds MEAI's wrapper. Configure an OpenTelemetry listener/exporter for its source and meter separately; creating a wrapper does not create a PostgreSQL execution store.

[OpenTelemetryChatClient](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI/ChatCompletion/OpenTelemetryChatClient.cs) emits request/response model metadata, duration, and available token data. It follows evolving GenAI semantic conventions. `EnableSensitiveData` defaults to false unless `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`; explicitly set the property when behavior must not depend on environment. Content capture can include messages, tool arguments/results, and additional properties. It cannot recover a template's original placeholders from already formatted messages.

The inspected usage/reporting types represent tokens and other available usage, not a provider price catalog. `ITokenCostEnricher` remains new LlmCmd work. It should preserve unknown usage as unknown and attach the pricing revision, provider/model, currency, and billable categories used. Reasoning and cached tokens can overlap other token categories; pricing rules must define how each provider accounts for them. A cost estimate is not an invoice.

Recommended collector fields are a design proposal: execution ID; stable prompt ID; declared revision; effective template revision/hash and provenance; raw template; original and effective typed parameter snapshots; rendered messages; caller member/file/line; requested route/model; effective settings snapshot; actual model/provider per attempt; usage; cost estimate and pricing revision; cache disposition; timing; response; outcome; and completion state. Store a schema version. Decide capture and retention policy for durable prompt content separately from telemetry export.

Retain immutable snapshots rather than live mutable `ChatOptions`, dictionaries, tool objects, or native SDK objects. Include formatter/culture and tool/config revisions where replay depends on them. Provider defaults can remain unspecified even after capture; reproducible replay requires pinning those settings, not merely recording null.

## Evaluation integration and retention

[IEvaluator.EvaluateAsync](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation/IEvaluator.cs) directly accepts the request/history as `IEnumerable<ChatMessage>`, the `ChatResponse` being scored, an optional judge `ChatConfiguration`, optional evaluator-specific context, and cancellation. This is the clean adapter boundary from a stored LlmCmd execution. No custom evaluator transport is necessary.

The official [evaluation overview](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/libraries) distinguishes core abstractions, quality judges, non-LLM NLP metrics, safety service evaluators, reporting, Azure storage support, and the console report tool. Use a separate judge client/configuration from the application client. Offline deterministic validators can implement `IEvaluator`; judge-based quality and safety checks need their respective model/service access.

[ScenarioRun](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/ScenarioRun.cs) permits one evaluation per run and writes its result to the configured store during `DisposeAsync`. Use asynchronous disposal. [ScenarioRunResult](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/ScenarioRunResult.cs) persists messages, the model response, evaluation metrics, optional chat details, tags, and scenario/iteration/execution names.

[ReportingConfiguration](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/ReportingConfiguration.cs) wraps its supplied judge client to record turns, and optionally cache responses. [ChatTurnDetails](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/ChatTurnDetails.cs) contains latency, model/provider, usage, cache key, and hit status. These are details of calls through that configured client; they are not an automatic record of arbitrary earlier application executions. Neither the result nor these details replace LlmCmd's raw-template/parameter/revision record. Link them through execution IDs/tags and keep application spend separate from judge spend.

For replay, materialize the stored messages and response, create a scenario using prompt ID/revision plus a dataset case identity, and evaluate that response. For a fresh experiment, rerun the command with explicit prompt/config/model revisions first, then evaluate the new response. Use a new execution name for each experiment; the official [reporting tutorial](https://learn.microsoft.com/en-us/dotnet/ai/evaluation/evaluate-with-reporting) explains that reusing the default execution name overwrites prior run results.

Retention is not one setting:

- The disk-based evaluation response cache defaults to **14 days**, as defined by [Defaults](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/Defaults.cs). [DiskBasedResponseCache](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/Storage/DiskBasedResponseCache.cs) checks expiration when reading. [DiskBasedResponseCacheProvider](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/Storage/DiskBasedResponseCacheProvider.cs) exposes explicit expired-entry deletion/reset. Cache expiry is not a general data-erasure guarantee.
- [DiskBasedResultStore](https://github.com/dotnet/extensions/blob/25f07afa51034e37b334210642d7dc5f191c142d/src/Libraries/Microsoft.Extensions.AI.Evaluation.Reporting/CSharp/Storage/DiskBasedResultStore.cs) writes JSON results and exposes deletion operations. No automatic result TTL is established by the inspected code. The application must manage result retention and exported HTML reports.
- LlmCmd's own PostgreSQL records, telemetry exports, external model-provider retention, and any Redis override history each require their own policy. This research did not verify provider-specific retention terms.

## Three grounded API approaches

**Constructor-first commands.** Generate an immutable descriptor whose constructor accepts all required typed values, as SKPromptGenerator does. Add fluent optional settings and execution methods. This is the smallest implementation, gives ordinary compiler errors for missing required arguments, and has no staged-type growth. It does not allow setting required parameters one at a time in arbitrary order.

**Staged fluent commands.** Generate a sequence of interfaces/types that exposes execution only after required values are supplied. A fixed order requires a small linear sequence; arbitrary order for independent required parameters can require a state for each subset unless another encoding is used. This meets fluent completion rules but adds generated API and diagnostic complexity. Runtime overrides still need validation because compile-time stages cannot prove the shape or values of externally supplied templates.

**Typed parameter object plus fluent command shell.** Generate a parameter record/class with constructor-required values, then support `WithParameters`, model/options overrides, and executor calls. This preserves a convenient immutable typed snapshot and is a good match for collection/replay. `required` members can help object initialization but do not provide a general staged fluent guarantee or validate deserialized/external data. Prefer this or constructor-first for the initial production contract; add staged helpers if the call-site benefit is demonstrated.

All three can use a closed result hierarchy on the requested C# 15 target. Expected missing/invalid override data, unavailable prompt/configuration, cancellation, provider failures, and output-parse failures need explicit result cases at the executor boundary. MEAI and SK APIs themselves still use exceptions; the executor must translate selected expected failures rather than claiming those dependencies are exception-free.

## What remains unverified

No live provider execution, service retention contract, pricing table, Redis/Pg adapter behavior, or real paid evaluator request was tested here. No universal model-option support is implied. Streaming completion, abandonment, usage availability, cache attribution, middleware ordering, and source-generator failure cases need focused spike checks. The root integration work owns executable verification and the final SDK/compiler target.

## TUnit follow-up for the test spike

Checked 2026-11-01 from [tunit.dev/llms.txt](https://tunit.dev/llms.txt) and its linked Markdown pages. The [live NuGet index](https://api.nuget.org/v3-flatcontainer/tunit/index.json) reports **TUnit 1.78.0** as the latest stable version. This research did not execute it under .NET 11.

**Runner.** TUnit uses Microsoft.Testing.Platform (MTP). Its [installation guide](https://tunit.dev/docs/getting-started/installation/) specifies an executable test project, the `TUnit` package, and no application `Main`/`Program.cs`; TUnit supplies the entry point. Remove `Microsoft.NET.Test.Sdk` and Coverlet packages. The meta package includes MTP coverage and TRX reporting extensions.

**.NET 11 invocation.** Microsoft's current [dotnet test reference](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test) supports selecting MTP through `global.json` at `test.runner`, or through `DOTNET_TEST_RUNNER=Microsoft.Testing.Platform` starting with .NET 11 Preview 6. That environment value overrides the file. MTP 1.7+ is required. In native MTP mode, platform flags can be passed directly; `TestingPlatformDotnetTestSupport` is unnecessary. Use explicit `--project` or `--solution` selection when needed. See the [MTP command reference](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-test-mtp). TUnit's current [FAQ](https://tunit.dev/docs/troubleshooting/) agrees; older running/CI pages still show the pre-.NET-10 forwarding form, so interpret those examples in their runner context.

**Assertions.** Every assertion must be awaited; building an assertion without awaiting it does not execute the check. The analyzer catches missing awaits. Current core methods include `Assert.That(...).IsEqualTo(...)`, `IsTypeOf<T>()`, `HasSingleItem()`, `Contains(predicate)`, `IsNotNull()`, and `.Member(...)`. Type/item assertions can return the checked value for later checks. Prefer asserting the concrete result case and its fields for expected-error results. See [Getting Started with Assertions](https://tunit.dev/docs/assertions/getting-started/) and [Awaiting](https://tunit.dev/docs/assertions/awaiting/).

**Reports and CI.** Enable TRX with `--report-trx`, select its name with `--report-trx-filename`, and set `--results-directory`. Coverage uses `--coverage` and `--coverage-output-format cobertura` when an interoperable coverage artifact is needed. The [current HTML report guide](https://tunit.dev/docs/guides/html-report/) says HTML reports are on by default and a `.tunit-report.json` sidecar accompanies them; `--report-html` is deprecated for TUnit's own reporter. Reports include Activity timelines, useful for collector integration tests. GitHub summaries activate from `GITHUB_ACTIONS` and `GITHUB_STEP_SUMMARY`; upload artifacts in an `always()` step so failures retain evidence. Do not assume a TUnit JSON sidecar has Jest/Vitest format. Keep TRX/HTML/JSON as native artifacts, and convert to the UI's supported test schema if necessary.

For multiple projects/jobs, the [aggregation guide](https://tunit.dev/docs/guides/report-aggregation/) documents `TUNIT_AGGREGATE_REPORTS=defer`, a shared `TUNIT_AGGREGATE_DIR`, and `TUnit.Reporting.Tool`'s `tunit-report merge` with `--github-summary` and optional `--fail-on-failures`. These are optional presentation features; the actual test process exit code remains the execution gate. The test owner should confirm available flags against the pinned package's `--help` and preserve a nonzero failure result. Root owns Aspire execution research; vendor OTel adapters are outside this research scope.
