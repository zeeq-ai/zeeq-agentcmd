# Runtime prompt experiments

**Status: design record.** This document records the proposed behavior and acceptance goals. For the implemented API and its current limits, see [Runtime experiments](../content/2.guides/7.runtime-experiments.md).

The implementation uses one atomic `IExperimentSnapshotSource` rather than two public source ports. A host can join separate prompt and parameter stores behind that port. Its optional cache is a process-local single-flight cache, not `HybridCache`. Composition shadows are explicitly offered through `CompositionShadowCoordinator` after the primary pin exists. Explicitly clearing an inherited sampling setting is not supported. The original proposals below should be read in that context, not as claims that every proposed adapter or control has shipped.

An application should be able to try a new prompt, model, platform, or sampling configuration while it is running. A prompt source supplies the template, and a parameter source supplies any permitted overrides and execution settings. The application keeps its typed command call. When a result is graded later, the grader can see the configuration and attempts that produced that exact result.

The original design shows separate prompt and parameter providers. The existing [execution-capture spike](../../research/spikes/ExecutionCapture/README.md) explored that idea, but its executor is not part of the library. Today, generated templates are constants, and composition freezes a rendered invocation when a part is registered. The ledger stores output JSON but does not attach the command snapshot to the output. These are the main gaps to close.

## A concrete example

Suppose `invoice.extract` has a compiled template and an input with `Document` and `Locale`. The command author permits an external override for `Locale`, but not for `Document`. The host has registered both an OpenAI and an Anthropic client pipeline.

1. The host selects a control or treatment assignment for a request. The host supplies that assignment; LlmCmd does not invent one from a trace ID.
2. A source publishes a new treatment containing a new template, `Locale = "fr-CA"`, an Anthropic model, and compatible sampling settings. The running application does not rebuild or restart.
3. A later call uses the existing `WithParameters(input).ExecuteAsync(ct)` shape. LlmCmd resolves the treatment, validates the effective typed input and route, and sends the rendered prompt through the selected host-owned MEAI pipeline.
4. If the external source fails before selection, the host's complete configured default runs. The result records that fallback and the settings actually used.
5. The result records the assignment, source and revision, effective templates, parameter origins, route and attempts, and output reference. An evaluator can read and grade the exact stored output or composed whole.

The example must actually update a source while the same process is running. Use a local file-backed source and a fake `IChatClient`; no credentials or paid calls are needed. The default ledger is in memory, so the example must not claim restart durability.

## Source and cache boundaries

Keep separate prompt and parameter source adapters, as in the diagram. A host-supplied coordinator owns publication of the versioned experiment view, which also contains the route and sampling settings. It may be part of either source or a separate adapter; it does not require a separate service. A view contains all values or names immutable revisions in the sources. It exposes a version-addressed command lookup so a deferred step can resolve against the same view. An unversioned pair of unrelated reads cannot promise an atomic publication. A host may wrap existing prompt-management or configuration systems behind these ports; core does not depend on their SDKs.

The view identifies the command, compatible command contract, source revision, experiment and variant where applicable. Compare the command revision and a generated signature of the input, output, allowed placeholders, and overridable fields before applying a release. The placeholder signature includes which scalar names are usable and which properties are ignored. Keep this signature separate from the compiled template hash, so changing the baseline text does not by itself change the shape. A type signature cannot prove that an arbitrary validation hook has the same behavior; authors must revise the command when that contract changes.

The host owns assignment, publishing authority, and any tenant or user targeting. An optional host-supplied selector receives the authenticated actor and captured operation context and returns an experiment selection. It can use an existing feature-flag service or explicit host context. Without a selector, use the source's published control configuration, or the locally configured default if the source explicitly has no override. Record which path ran; do not invent an experiment arm. A standalone execution selects once; a composition selects once for the root and stores the selection with its draft pin. The selection can identify a bundle of coordinated variants, so deferred commands need not be known in advance. `TrialId` remains correlation, not authorization or proof of assignment. Read only what the selection needs; do not send caller input to a configuration source by default. The runtime is a singleton, so source adapters must be singleton-safe or create and dispose a scope for scoped dependencies.

Use a .NET cache as an optional source decorator. Start with `HybridCache` backed by local memory and a configurable **30-second absolute expiration** for the latest reusable experiment definition. It coalesces concurrent misses within one cache instance; a host may add a distributed cache. Do not change the host's global cache settings. Cache definitions and their versioned command entries, not per-user selections or caller input. Keys include the source, authenticated tenant or other authorized partition, version and command ID where applicable, and every other dimension that affects the cached value.

After the latest-definition entry expires, the next lookup checks for an update. Specific versions are immutable and may be evicted independently for memory management. Expiration does not guarantee simultaneous rollout across nodes, and it does not determine how long a draft remains bound to a version. A call holds an immutable resolved view for its lifetime. A draft records its pin in its authoritative store. If an old revision is evicted, read that exact revision again or use a separately retained snapshot; never substitute `latest`. If neither is available, report the failure without another model call.

If the external source fails before a call or draft selects its view, run the **configured default**. This is a complete fallback view available locally: the host may configure its templates, parameter defaults or overrides, route, and sampling; otherwise it uses the command's compiled templates, caller parameters, and authored or host default profile and settings. Do not make the fallback depend on the same unavailable source. This rule also applies when an explicitly requested external version cannot be fetched; record that the requested version did not run. A valid explicit call-site setting still takes precedence. Use the default as one complete unit; never combine a treatment template with default parameters or routing. Record the effective source as default and a bounded reason such as unavailable, timeout, incomplete view, or invalid release. Do not label the result as treatment.

A valid, unexpired cached view remains usable until its expiration. Once a lookup fails, use the configured default rather than silently extending a stale cache entry. A source's explicit `no override` result also selects the default, with a distinct reason. Propagate caller cancellation instead of making a default model call. Actor or run authorization failures remain failures; default selection cannot grant access. Use bounded source timeouts, and do not cache invalid source values as successful releases.

HybridCache's optional distributed layer needs AOT-safe serialization. Test the actual package-only NativeAOT consumer, including a cache miss and an update. Microsoft documents the [cache's per-instance miss coalescing](https://learn.microsoft.com/en-us/dotnet/core/extensions/caching) and its [NativeAOT serialization requirements](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/hybrid?view=aspnetcore-10.0).

## Templates and typed overrides

Keep the compiled command, input type, result type, and generated schema authoritative. An external view can inherit, replace, or remove the system template, including adding one when the compiled command has none. It can inherit or replace the user template, but cannot remove it. A replacement user template and the effective rendered user message must contain non-whitespace text. If a fresh treatment renders blank, try the complete default; if that also renders blank, fail without a model send. Once a composition is pinned, a blank deferred part fails without changing the pin. The representation should leave room for ordered messages, but must not claim multimodal or tool-message support without contract tests.

The generator emits a table of allowed scalar placeholders and their typed accessors. A runtime parser uses the same grammar as the generated renderer, including escaped braces, case rules, and invariant formatting. Validate unknown names, unsupported types, malformed braces, and configured size limits before a model request. Substituted values are data and are not parsed again. Differential tests compare runtime rendering with the existing generated renderer for the same template and inputs.

External values may replace only input properties that the command author explicitly marks as overridable. The source addresses them by their case-sensitive CLR property names, matching the template grammar; a JSON serialization name is not an alias. Omitted values keep the caller's values; an explicit null is accepted only where the property allows null. Reject unknown, unauthorized, duplicate, wrongly typed, or out-of-range overrides as one batch. A structurally invalid release selects the complete configured default before selection and records a bounded reason. Run the command's typed validation on the **effective** input, and render and capture that same input. If known input makes a treatment invalid before selection, try the complete default and validate it; if that is invalid too, return an input failure without a model send. A deferred input that fails validation after a draft is pinned fails that step without changing the pinned view. Capture origins without guessing which party caused a cross-field failure. Hosts may apply stricter policy to sensitive fields.

The first implementation should prove typed overrides for a narrow, generator-verifiable immutable record shape and scalar properties. Start with a sealed record whose overridable properties are scalar positional or auto-properties with `init` accessors. Reject custom copy constructors, mutable state, and stored derived state that could become stale when an overridable value changes. All retained members must be in a provably immutable allow-list. Generate typed per-property application code and clear diagnostics when that proof is not possible; a shallow `with` copy alone is not proof of deep immutability. Do not clone a whole input by serializing and deserializing it: an omitted null can become a constructor default. Investigate an explicit host-supplied snapshot/mapper for other DTO shapes as a follow-on. This limit applies to runtime overrides, not to ordinary commands or template-only changes.

## Runtime routes and sampling

An experiment can select either a configured profile or a validated route in its versioned view. The route names a host-registered client pipeline and a model or deployment, plus sampling and inference settings such as temperature, top-p, top-k, output-token limit, and reasoning options. A change of client must supply a compatible model or select a complete profile; do not carry an unrelated model across platforms. Extend the typed options as needed for other supported MEAI settings, such as seed, penalties, and stop sequences. Validate every supplied field; do not silently ignore one that the selected provider or model cannot accept. Preserve the distinction between an omitted setting and an explicit request to clear an inherited value.

The existing router freezes profiles at startup and only constructs clients referenced by those profiles. Looking up an external profile name alone therefore cannot switch to a newly specified model in a running process. Split long-lived, host-owned client registrations from immutable, versioned route snapshots. Build an unreferenced registered pipeline lazily on first use, with thread-safe single creation; dispose runtime-owned clients once and leave DI-owned clients with DI. A request uses a validated route snapshot without rebuilding the router or disposing a pipeline used by another request. Keep retry, provider fallback, per-attempt capture, and the host's global execution budget in the same MEAI routing path.

The host must register and authorize the client pipelines, endpoint, credentials, model/deployment bindings, and route policy. A per-request-model client can use an allowed new model without a new static profile or restart. A model-bound client can select only its bound target; a host that needs new model-bound targets without a restart must provide an approved runtime client factory and safe lifetime policy. An Azure deployment name is not proof of its underlying model: keep an explicit target binding. A platform with no host registration or credentials cannot be created by external experiment data alone.

Validate a release against registered clients, fixed-model bindings, allowed targets, sampling limits, and host retry, timeout, and cost controls before it can be selected. The provider package can supply model-capability and binding validation through a core-neutral interface; the existing MEAI model-policy middleware remains a final check. Model-specific fixed or unsupported temperature and reasoning rules must be enforced. If release validation fails, choose the configured default before the first model send and record a sanitized reason. Unknown prices remain unknown, never zero.

Select the base route from the command's authored profile or the host default. A valid external route may replace that base. An explicitly selected invocation profile wins over external route selection. External sampling values are defaults of the route node they configure, not global request overrides: each fallback uses its own route defaults. Explicit invocation settings take precedence and may flow to fallback attempts, subject to the target model's validation. Command and provider defaults fill remaining fields. A dynamic primary route may reference an approved host-configured fallback chain; pin and fingerprint the entire chain and the shared budget. Record the intended treatment and the effective setting origins when a caller override changes what actually runs.

## Execution and composition

For a standalone command, capture operation context and the authenticated actor, authorize the source lookup, resolve the version or complete default, apply and validate overrides, then freeze the effective templates, values, route, and sampling settings before the first model attempt. Retries and provider fallback routes reuse the prepared base messages and pinned route graph. Provider fallback after a model send is different from external-source fallback: it follows the authorized route policy and must not silently substitute the default prompt or discard the failed attempt. MEAI middleware remains in the host's pipeline; if middleware changes a request, per-attempt capture must distinguish what the command prepared from what the provider actually received.

Composition needs an extra boundary:

1. `BeginAsync` already opens or reopens a draft. Registering a part must still freeze caller inputs without source I/O or model calls. For template-only changes on mutable input, capture every allowed scalar placeholder as its invariant-formatted string at registration, along with the existing cloned parameter projection. The runtime renderer uses those frozen strings, not a later read of the caller's object.
2. At `ExecuteAsync`, authorize the actor and validate the plan. Resolve and materialize one complete immutable experiment view, or the complete configured default when the source fails. Atomically pin its identity and retained content on the existing draft before any slot claim or model send. If two implicit `latest` selections race, the loser discards its candidate and loads the winner's exact pin. This also applies when two authorized actors selected different arms for the same draft: the stored selection is the one that ran and must be used for analysis. A conflicting explicit pin reports a conflict before any claim or send.
3. Prepare each slot against the retained pin. A deferred `Then` callback can choose a command only after its dependency is stored, so the materialized view must support those lookups without knowing every command at the start or depending on the external source remaining online. The first release treats experiment overrides as data available in this view; application data derived from a previous step still comes through the deferred invocation's typed parameters. Reopen and replay read the stored pin; they do not resolve `latest` again. To run a new view, use a new draft key or trial; do not repin an existing draft.
4. Fingerprint the effective version, assignment, templates, frozen placeholder strings, values, and existing route settings before the claim. Full evidence capture records the same effective placeholder strings used to render; a redacted capture must say what was omitted. Keep explicit reused-part provenance, including the part's original experiment identity. Never relabel an old part as though it ran under the new treatment.

The store currently permits a failed or cancelled slot to be reclaimed. A fingerprint alone therefore does not pin an entire draft. Extend `ICompositionStore` with a conditional pin operation and test concurrent handles. Retain the journal's rule that an attempt with uncertain spend is not automatically resent. The in-memory store proves the contract only within one process; a durable implementation must persist the pinned view or a separately retained authoritative copy. If previously pinned content is irrecoverably unavailable after part of a whole ran, report that failure before another send. Substituting the default at that point would mix configurations inside the same whole.

The first engineering spike must prove the split between registration-time input freezing and async source resolution. It must also prove that typed validation receives exactly the values rendered and fingerprinted. If an input shape cannot meet both guarantees, reject runtime overrides for that shape rather than silently changing existing composition behavior.

## Parallel comparison with one primary

A host may opt into running one primary variant and several **shadow** variants for the same application input. The primary is the only result returned to the caller. Shadows are independent evaluation runs: they never replace the primary result, including when the primary fails, and the caller does not wait for their results. This is different from an A/B split, where each input normally runs only its assigned variant.

Resolve one experiment view, freeze the caller's input and authorized context, and select the primary and shadow variants from that view. Each variant applies and validates its own permitted overrides and receives the same frozen caller input. The ordinary `Invocation` holds a reference to its parameter object, so parallel branches must not assume that the current wrapper deep-freezes mutable inputs. Capture a safe immutable snapshot or reject a shape that cannot be snapshotted correctly. Do not use whole-object JSON round-tripping as a shortcut.

Start the primary and offer shadow work promptly to a host-owned, bounded and supervised queue. A worker can run accepted shadows concurrently with the primary, but it may start later when capacity is busy. It must own its service scope, use captured values rather than a request scope or ambient context, and enforce authorization again as required by the host. Give shadows independent timeouts and a shutdown policy. Define whether an accepted shadow continues when the caller cancels; primary completion alone must not silently cancel it. An in-memory queue and the default ledger can lose work on restart; hosts that need durable comparisons must supply durable work and evidence storage with recovery and idempotent claims. Do not automatically retry an attempt whose provider spend is indeterminate.

The host controls whether shadows run, the sample rate, variant count, queue capacity, concurrency, and group-wide attempt and time limits. A cost limit can be applied when cost is known; unknown prices or usage cannot establish a hard billing cap. Reserve capacity for the primary: the existing route budget is per invocation and does not cap the total across variants. Queue full, source failure, validation failure, shadow failure, and shutdown can skip or abandon a shadow; record those outcomes where possible without changing the primary. If the source is unavailable and the configured default runs, skip source-defined shadows unless the host explicitly supplies a valid local comparison plan. Parallel calls share provider resources, so primary latency and rate limits can still be affected.

Each variant has its own execution and attempt IDs, role, effective settings, and exact stored `OutputRef`. A comparison-group ID links them to the same input and primary without granting access. Mark shadows so their results cannot be mistaken for user-visible outputs; do not count a shadow as a user exposure. For composed variants, use separate trial or draft identities and store and grade each variant's exact whole. Never attach shadow parts to the primary draft or reconstruct a whole from telemetry. Use only host-approved, side-effect-free pipelines and data destinations for shadows; do not duplicate tool actions or other application side effects.

## Evidence for evaluation

Extend the execution snapshot with the compiled definition identity and the effective source identity separately. Record the effective system and user templates, effective parameter values and their origins, experiment and variant, source and revision, selected platform/client, requested model or deployment, and effective sampling settings. Each attempt records the actual platform, requested and reported model, sampling values when observable, usage, and any provider fallback. A hash can identify content; it is not a substitute for retaining authorized content or an immutable version that can be read later.

Link experiment evidence to the exact stored leaf output and to the composition's stored whole and member lineage. The current `OutputArtifact` and ledger write do not carry the execution snapshot, so this needs an explicit ledger or composition-store contract change. Write an output and its evidence atomically under the same producer identity, or use a durable, idempotent pending protocol that recovers the evidence by exact output reference. A leaf cannot attach and a whole cannot seal as gradeable until its evidence is confirmed. Repeated writes must compare both output and evidence, and return the same artifact or a conflict. An implementation with separate stores must prove its recovery protocol; a telemetry event is not a substitute. Grading still targets the whole's exact `OutputRef`. A reused part keeps its original producer and experiment evidence.

Emit bounded version and variant metadata to OpenTelemetry and relevant adapters. Do not put a string-valued release ID into an adapter's integer prompt-version field or reuse the output schema version for the experiment version. Text and parameter values need an explicit host capture, redaction, access, and retention policy. Sinks and telemetry remain best effort: they are not the authoritative evidence store, and a trace link alone does not guarantee an evaluator can reconstruct a result.

## Delivery sequence

1. **Prove the hard seams.** Spike dynamic rendering, typed scalar override application, registration-time freezing, and a fake versioned source. Prove NativeAOT and preserve the existing generated-template behavior.
2. **Add sources and cache.** Define the prompt source, parameter source, consistent-view coordinator, failure results, authorization inputs, DI lifetimes, and optional short-lived .NET cache. Supply a fake and a file-backed source.
3. **Integrate standalone execution and routing.** Apply source values before typed validation and rendering. Add immutable dynamic routes over host-registered clients, model-policy validation, typed sampling precedence, and configured-default source failure. Preserve MEAI middleware, cancellation, ownership, retry budgets, and the existing closed outcome model.
4. **Pin composition.** Add the draft compare-and-set pin, version-aware preparation for direct and deferred steps, identity checks, and explicit reuse provenance.
5. **Connect evaluation and telemetry.** Store evidence with the exact output and aggregate lineage; map bounded metadata into the existing observers and exporter adapters.
6. **Add opt-in parallel comparisons.** Start with leaf commands, a primary result and a bounded shadow worker. Add composition shadows with separate drafts and exact aggregate grading after the leaf path passes its gates.
7. **Document and demonstrate.** Add a reader-friendly guide, a running-process file update example, primary and shadow comparison, a composition and whole-grade example, source-author guidance, and honest limitations. Update builder analyzer recognition if the new setup adds fluent methods.

## Acceptance checks

- A running process observes a new external template, permitted parameter value, platform, model, and sampling settings after cache expiration without rebuilding or restarting. Fake OpenAI and Anthropic pipelines verify the selected client and actual `ChatOptions`, including a model not declared in a startup profile. A disabled source still runs the configured default.
- Cache tests cover concurrent misses, expiry, two tenants, caller cancellation, source timeout, invalid data, fallback to a locally configured complete default, and separate nodes. Verify the default's templates, parameter values, client, model, and settings as one unit. A cached value is never treated as authorization.
- Route tests cover a fixed-model mismatch, an unregistered or unauthorized client, an unknown model policy, an Azure deployment binding, unsupported or fixed sampling values, field precedence, an unknown price, provider retries and cross-platform fallback. Invalid external routes fall back before any send to the rejected target. A fallback uses its own route-level sampling defaults; only explicit invocation overrides flow across the chain.
- Template tests cover grammar parity, escaped braces, unknown names, injection-shaped values, formatting, and system and user templates.
- Override tests cover actual typed input, opt-in enforcement, missing versus null, wrong types, stale command contracts, validation hooks, unsupported mutable shapes, and no partial merge after failure. An invalid treatment with a valid configured default uses that default before selection; invalid deferred input does not change a pinned draft.
- Composition tests rotate or stop the source between registration, execution, retry, and a deferred `Then` step. They exercise concurrent default-versus-treatment draft pins, recovery without repinning, retained historical views, explicit reused parts, and the no-extra-send journal rule.
- Parallel comparison tests block a shadow while the primary returns, mutate the original input after scheduling, and verify separate identities and the same frozen base input. Cover shadow errors, queue saturation, cancellation and shutdown, authorization and scope lifetime, side-effect refusal, source-default fallback, independent budgets, and distinct composition drafts and stored wholes.
- Evaluation tests read each stored part and whole, inspect the effective experiment evidence, and grade the exact aggregate `OutputRef`. They cover evidence-write failure, a crash between recording and attachment or sealing, and concurrent replay of matching and mismatched evidence. They do not infer a grade target from a trace or a component execution ID.
- A fresh package-only NativeAOT consumer exercises both sources and the cache with reflection disabled. Offline TUnit tests, examples, build, and formatting checks pass; live provider tests remain explicitly opt-in.

## Decisions to confirm during implementation

- The initial override shape is intentionally narrow. The spike decides whether a safe generated mapper or an explicit host mapper can support more existing DTOs without weakening freeze and validation.
- System and user text are the first supported message shapes. Decide whether ordered multi-message templates are needed in the first release rather than implying support.
- The host supplies experiment assignment. External settings include platform, model/deployment, and sampling; a built-in bucketing engine and provider-specific prompt-management adapters are separate features. Fallback profiles reuse the prepared prompt; model-specific fallback templates are not included.
- A 30-second cache lifetime is a starting default, not an update-delivery guarantee. Hosts with stricter consistency can use a shorter lifetime, explicit version selection, or their own source and cache.
- The configured default is the source-failure policy. Define host limits for dynamic targets and choose how immutable views are retained so a pinned composition does not need the external source after its first send.
